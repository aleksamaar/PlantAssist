## Что это

Веб-приложение для учёта домашних растений: полив, подкормка, пересадка, обработка
от вредителей, витамины, цветение, черенки, посевы, архив, достижения, статистика.

**Развёрнуто в облаке** (PythonAnywhere) — там источник правды. Локально запускается
для разработки; локальные данные при этом устаревшие. Подробности — в STATUS.md.

## Команды разработки

```bash
py app.py            # локальный сервер (браузер откроется сам через 1 сек)
start_local.bat      # то же, с предупреждением про устаревшие данные
backup.bat           # скачать бэкап из облака в backups/
```

После изменения `app.py` сервер нужно перезапустить вручную (`debug=False` намеренно).
Тестов и линтера нет — всё проверяется руками в браузере.

**HTTPS-режим:** если существуют `certs/server.crt` и `certs/server.key`, `app.py`
стартует по HTTPS. Иначе — обычный HTTP. Сертификаты создаёт `gen-certs.sh`.

### Деплой

Тестов и линтера нет, а деплой сразу в бой — поэтому перед пушем: `/code-review`
(поиск багов), затем проверка вживую в браузере.

```bash
git add -A && git commit -m "..." && git push   # 1. локально
# 2. PythonAnywhere → Consoles → Bash: cd PlantAssist && git pull
# 3. PythonAnywhere → вкладка Web → зелёная кнопка Reload
```

### Правка `.bat`

Все `.bat` — **чистый ASCII + CRLF, без `chcp`**. Кириллица и UTF-8 в них ломают
разбор на англ. консоли (OEM 437): cmd съедает первые символы команд. При правке
не вставлять русский текст и не менять кодировку — Яндекс Диск уже один раз
перекодировал их и сломал запуск (подробности в STATUS.md).

## Модель данных

### data.json — растения

```json
{
  "id": "uuid4",
  "name": "Фикус",
  "description": "", "purchased_date": "2024-01-15", "price": 1200,
  "plant_types": ["🌿 Арроидные"], "problems": ["🕷 Паутинный клещ"],
  "watering_note": "", "light": "", "soil": "", "room": "Гостиная",
  "favorited": false,
  "is_flowering": false,
  "flowering_log": [{"date": "2026-05-01", "event": "start", "notes": ""}],
  "needs_repotting": false,
  "fertilizing_reminder_date": "",
  "mute_watering": false,
  "mute_fertilizing": false,
  "archived": false, "archived_date": "", "archive_reason": "",
  "photos": [{"id": "uuid4", "filename": "...", "date": "", "description": ""}],
  "watering":     {"frequency_days": 7,  "last_date": "", "history": ["2024-05-20"]},
  "fertilizing":  {"frequency_days": 30, "last_date": "", "history": [{"date": "", "fertilizer": "", "dose": ""}]},
  "repotting":    {"last_date": "", "history": []},
  "pest_control": {"frequency_days": 14, "last_date": "", "history": [{"date": "", "product": ""}]},
  "vitamins":     {"frequency_days": null, "last_date": "", "history": [{"date": "", "product": ""}]}
}
```

`flowering_log`: `event` = `start` | `end`, отсортирован от новых к старым.
Пары start/end образуют периоды цветения. При удалении записи `is_flowering`
пересинхронизируется по последней оставшейся.

### sowings.json — посевы

```json
{
  "id": "uuid4", "name": "Лимон Мейера",
  "sowing_date": "2026-07-01",
  "seeds_count": 10,
  "sprouted_count": 5,          // ← ВЫЧИСЛЯЕТСЯ из log, не задавать напрямую
  "first_sprout_date": "2026-07-08",  // ← ВЫЧИСЛЯЕТСЯ из log
  "expected_min_days": 7, "expected_max_days": 21,
  "substrate": "Грунт", "pretreatment": ["Замачивание"],
  "contents": ["Халапеньо", "Хабанеро"],   // «коробка»: несколько разных растений в одном посеве
  "notes": "", "status": "germinated",
  "log": [{"date": "2026-07-01", "event": "sown", "count": 10},
          {"date": "2026-07-08", "event": "sprout", "count": 2, "notes": "первые"}],
  "photos": []
}
```

`contents` — режим «коробки»: список того, что посеяно в один контейнер, когда там
разные растения. Всходы/статус при этом общие на всю коробку. Обычная строка-список,
входит в `SOWING_FIELDS` (меняется через PUT). Пустой список — обычный посев.

`log` — **источник правды** для всходов. `event`: `sown` | `sprout` | `pricked_out` | `note`.
`recompute_sowing()` пересчитывает `sprouted_count` (сумма всех `sprout`) и
`first_sprout_date` (минимальная дата `sprout`). Поэтому `sprouted_count` и
`first_sprout_date` **исключены из `SOWING_FIELDS`** — их нельзя менять через PUT.

`status`: `sown` | `germinated` | `pricked_out` | `in_collection` | `failed`.
Статус двигается вперёд автоматически при добавлении записи в лог, но никогда
не откатывается назад.

### cuttings.json — черенки

`{id, name, parent_plant_id, date_taken, method, status, notes}`
`method`: `water`|`soil`|`moss`. `status`: `rooting`|`rooted`|`planted`|`failed`.

### achievements.json — полученные достижения

`{"unlocked": {"water_100": "2026-07-27", ...}}` — id достижения и дата получения.

**Условия живут на фронтенде** (`ACHIEVEMENTS` в app.js), сервер только помнит, что
уже получено. Иначе плашку показать невозможно: 71 условие пересчитывается заново на
каждой отрисовке, и «новое» не отличить от «старого». Хранение на сервере, а не в
`localStorage`, — чтобы прогресс был общим для телефона и компьютера.

Дата первого получения не перезаписывается (`setdefault`). Сервер верит клиенту:
`POST` запишет любой присланный id — список достижений ему неизвестен.

При первом запуске файла нет, `GET` возвращает `initialized: false`, и фронтенд молча
записывает всё уже заслуженное **без показа плашек** — иначе за годы истории их
вывалится сразу сорок.

`price` — цена покупки в рублях, `null` если не указана. Чистится на сервере
(`_clean_price`): запятая как разделитель и пробелы разбираются, мусор и
отрицательные → `null`. **Ноль — валидная цена** (подарок), поэтому проверка на
пустоту явная: `value in (None, '', False)` съело бы `0`, так как `0 == False`.
Статистика считает траты только по растениям с ценой и подписывает, по скольким.

### Ключевая логика дат

- `next_date = last_date + frequency_days` — считается на фронтенде
- Пересадка: фиксированный год (365 дней), нет `frequency_days`
- `fertilizing_reminder_date` — разовое напоминание, сбрасывается при записи подкормки
- `history` — от новых к старым; запись = строка (дата) или объект `{date, ...}`
- Все функции дат работают в **локальном времени** (UTC+N корректен)

### Миграция

`load_plants()` и `load_sowings()` дополняют объекты недостающими полями при
загрузке (in-memory). Можно безопасно добавлять поля без правки JSON.
`load_sowings()` строит `log` из старых полей, если его нет.

## Безопасность и надёжность

- **Авторизация:** включается только при заданной `PLANTASSIST_PASSWORD`. Без неё
  (локально) приложение открыто. `@app.before_request` пускает без входа только
  `/login`, `/style.css`, `/manifest.json`, `/sw.js`, `/icons/*` — остальное 401
  (для `/api/` и `/photos/`) или редирект на логин.
- **Атомарная запись:** `_atomic_write_json()` — пишет в `.tmp` + `os.fsync` +
  `os.replace`. Сбой посреди записи не может побить данные.
- **Restore** проверяет ZIP, валидирует JSON до записи, и берёт `basename()` от
  путей внутри архива — защита от path traversal.

## Фронтенд (static/app.js)

SPA без роутера, вся логика в одном файле.

```js
let plants = [];        // активные растения
let cuttings = [];      // черенки (лениво)
let sowings = [];       // посевы (грузятся при старте — нужны для напоминаний)
let archivePlants = []; // архив (лениво)
let currentView = 'today';
```

После изменения на сервере локальный объект патчится ответом сервера, затем `render()`.

### Навигация

Роутера нет, URL не меняется. 8 экранов переключает один обработчик на
`.sidebar-nav-btn`: снимает класс `active` со всех `.view`, вешает его на
`#view-<currentView>` и зовёт нужный `load*()`/`render*()`. Значения `data-view`
объявлены в `index.html`:

`today` · `all` · `calendar` · `cuttings` · `sowings` · `archive` ·
`achievements` · `stats`

Мобильная шторка «Ещё» логику не дублирует: она кликает по соответствующей
кнопке сайдбара (`.sidebar-nav-btn[data-view="…"]`). Новый экран = разметка
`.view` в `index.html` + кнопка сайдбара + ветка в обработчике.

### Заглушение напоминаний

- `isWateringMuted(p)` → `mute_watering`
- `isFertilizingMuted(p)` → `mute_fertilizing` **или есть активные `problems`**
  (больное растение не удобряют — авто-пауза)

Учитывается в `getCardStatus()`, `hasOverdueTasks()`, `renderToday()`,
`renderTodaySummary()` и `CAL_ACTIONS` календаря.

### Достижения

`ACHIEVEMENTS` — массив с `check()`. Важно: **обработка от вредителей считается по
уникальным дням** (`_uniqueDays('pest_control')`), а не по сумме записей — она
делается всем растениям сразу в один день. Полив/подкормка считаются по записям
(они индивидуальны). `_totalCare()` использует то же правило.

## PWA

- `manifest.json` + `sw.js` + иконки. Регистрация SW — в конце `index.html`.
- **Стратегия кэша:** `/api/` и `/photos/` — network-first (свежие данные);
  свой HTML/CSS/JS — network-first (обновления видны сразу); иконки/CDN — cache-first.
- Установка PWA и service worker требуют **доверенного HTTPS** — работают только
  из облака. По локальной сети с самоподписанным сертификатом Chrome их блокирует.

## Дизайн-система

Палитра «Sage + Terracotta»: тёплые нейтралы, тёмно-зелёный сайдбар, шрифт
**Manrope**. Исходники редизайна — в `design/feedback/` (папка в `.gitignore`):
макеты, скриншоты всех экранов и токены.

**Всё живёт в токенах** `:root` / `body.dark` в начале `style.css`. Хардкодить цвет
в правиле нельзя — тёмная тема работает переопределением тех же переменных.

Два подводных камня, из-за которых уже ломалось:

- **`--sage-dark` и `--sage-dark-bg` — разные роли.** Первый это цвет текста и
  иконок, в тёмной теме он светлеет до `#86AE79`. Второй — заливка (сайдбар,
  `.btn-primary`, активный фильтр-чип) и **не переопределяется** в тёмной теме.
  Если использовать `--sage-dark` как фон, в тёмной теме сайдбар станет салатовым.
- **Сайдбар одинаков в обеих темах.** Правил `body.dark .sidebar*` быть не должно.

`--red-muted` — только кольцо карточки «есть проблемы»; яркий `--red` на тёплом
фоне читается слишком резко. Разделитель в подвале карточки втянут по бокам
(`left/right: 12px`), чтобы не упираться в это кольцо.

Цвета графиков берутся из тех же токенов через `_cssVar()` в `_chartTheme()`:
одиночные серии — `--chart-2`, сегменты пончика — `--chart-1..6`.

## Нюансы

- **`static_url_path=''`** — статика раздаётся с корня, поэтому API под `/api/`
- **Lucide:** `createIcons()` заменяет `<i>` на `<svg>`, поэтому при динамическом
  обновлении иконки нужно пересоздавать элемент через `innerHTML`, а не искать `<i>`
- **`--text-secondary`** — алиас `--text-muted` (в JS есть inline-стили с ним)
- Фото хранятся файлами, не в base64
- Сервер слушает `0.0.0.0` — доступен по локальной сети
- Тёмная тема — класс `body.dark`, сохраняется в `localStorage`
- `GET /api/plants` не возвращает архивные
- `archive_reason` — свободная строка; в модалке архива фронтенд склеивает
  выбранную причину-чип и комментарий в вид «Причина — комментарий»
- **Индекс ухоженности** (`careScore`) считает долю поливов/подкормок/обработок,
  уложившихся в заявленную частоту с допуском `CARE_TOLERANCE`. Кроме завершённых
  интервалов учитывается ещё и открытый (последнее действие → сегодня) — без него
  забытое растение просто не попадало бы в метрику. Заглушённые растения пропускаются
- **Период** на экране статистики — `statsMonths` (3/6/12), им же управляются
  графики по месяцам через `_monthLabels(MONTHS)`
- **Цвета графиков** проверены валидатором различимости, не подобраны на глаз:
  `ct.duo` — две ступени одной гаммы для двухсерийного графика (сейдж и олива
  различались на ΔE 5.8 при пороге 15 — их не различить даже с обычным зрением);
  `ct.ramp` — монотонная рампа для пончика, хвост сверх шести типов сворачивается
  в «Другое». Менять эти значения на глаз не стоит
- **Проверка достижений висит на `api()`**: после каждого успешного не-GET запроса
  ставится отложенная (300 мс) проверка. Debounce обязателен — массовая обработка
  шлёт запросы пачкой. Загрузка фото идёт мимо `api()` голым `fetch`, но достижений
  по фото нет. Черенки грузятся при старте: без этого 11 «черенковых» достижений
  вывалятся пачкой при первом заходе на их экран
- **Страница логина** — HTML-строка `LOGIN_PAGE` внутри `app.py`, со своими
  инлайновыми стилями и своей тёмной темой. Правки `style.css` её не касаются
- **Загрузка фото не валидируется:** расширение берётся из имени присланного
  файла, тип не проверяется, `MAX_CONTENT_LENGTH` не задан. Репозиторий
  публичный, защита — только пароль приложения

Python >= 3.8 (на хостинге 3.13)
